> Purpose: convert Gate 3 from a blocker list into an executable launch program. Use this section with [Ecosystem/DEPLOY.md](Ecosystem/DEPLOY.md#enterprise-launch-plan) when moving from pre-launch to live backend rollout.

### Research Basis

| Source | Verified rule | Why it matters here |
|---|---|---|
| [GitHub reusable workflows](https://docs.github.com/en/actions/sharing-automations/reusing-workflows) | Reusable workflows must expose `workflow_call`, and environment secrets come from the called job's environment rather than the caller passing an environment through `workflow_call`. | `DEPLOY_*` must stay owned by `Ecosystem/infra`; node and matcher should reuse the infra deploy surface instead of duplicating SSH secrets in multiple repos. |
| [GitHub environments](https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment) | Required reviewers, wait timers, branch or tag restrictions, and environment secrets are enforced at the environment level. | Mainnet approval belongs on deployment environments, not in ad hoc workflow conditionals. |
| [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) | Deploys that share a target should serialize with a concurrency group; production deploys should not cancel in flight. | Node and matcher rollout must be serialized per service and network to avoid overlapping restarts. |
| [Docker Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/) | Compose waits for a container to be running, not ready; true dependency readiness requires `healthcheck` plus `service_healthy`. | Node, matcher, PostgreSQL, BPS, and data-service cannot be called production-ready without explicit health checks. |

### Workstream Details

#### 1. Ratify launch node topology — ✅ DONE

- Decision ratified: `node-scala` is the production node. `node-go` is archived.
- Matcher pairs with `node-scala` via gRPC (ScalaPB ↔ ScalaPB).
- No fallback node in scope; single-implementation strategy.

#### 2. Codify the managed runtime

- Add node and matcher to the infra runtime surface instead of relying on undocumented host procedures.
- Define persistent storage, log retention, restart policy, firewall exposure, DNS ownership, and backup/restore expectations.
- Keep secrets split across the three existing tiers: GitHub org or repo, infra environment, and `/opt/dcc/secrets/<network>.env`.
- Add health checks for every launch-critical dependency; Compose waiting for a process to be running is not sufficient for readiness.
- Done means a fresh host can be provisioned and converge into the intended node plus matcher runtime from code.

#### 3. Wire automated rollouts

- Reuse the infra deployment contract rather than inventing a second secret or SSH model.
- Serialize deploys by service and network so mainnet and lower environments cannot race each other.
- Keep mutable tags out of production rollout; deploy by immutable release tag or digest.
- Put reviewers and branch or tag restrictions on `mainnet` environments, not only in workflow prose.
- Done means stagenet and testnet rollouts are routine, auditable, and identical in shape to the eventual mainnet rollout.

#### 4. Verify and rehearse rollback

- Define explicit acceptance checks for node height, peer health, matcher readiness, BPS ingestion, data-service queries, and TLS reachability.
- Verify dependent consumers, not just producers: Exchange, Scanner, and Cubensis must all read the live backend successfully.
- Capture the previous release reference before every deploy so rollback is an input, not a reconstruction exercise.
- Require one production-equivalent smoke run before Gate 5 can be cleared.
- Done means the team can answer both "is it healthy?" and "how do we revert?" without improvisation.

**Security finding — i18next 26.0.6:**

The 26.0.4 → 26.0.9 bump is mandatory, not optional. Version 26.0.6 was a dedicated security release authored by the i18next team via internal audit:

1. **ReDoS** — `unescapePrefix`/`unescapeSuffix` were not regex-escaped when building the interpolation pattern. Attacker-controlled delimiter values containing `(`, `[`, `.` could produce catastrophic backtracking.
2. **Log injection (CWE-117)** — CR/LF/NUL and C0/C1 control characters in user-controlled translation keys, language codes, namespace names, or interpolation variable names were passed directly to `console.log` string arguments, enabling log forging.
3. **Nesting-options quote injection** — when `escapeValue: false` AND interpolated variables were used inside a `$t(key, {"{{var}}"})` nesting-options block, attacker-controlled values containing `"` could break out of the JSON literal and inject extra options (e.g. redirect `lng` or `ns`). Default `escapeValue: true` was unaffected.

## Common Migration Recipe

> Every package in this monorepo followed the same 4-phase migration pattern. This recipe is documented here for historical reference and as a template for any future forks.

### Phase 1 — Rebrand

1. Fork repository, update `package.json`: name to `@decentralchain/*`, author, repository, homepage
2. Replace Waves branding in README, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT
3. Replace Waves network URLs with DCC equivalents
4. Add governance docs (LICENSE, CHANGELOG, SECURITY.md)
5. Run `grep -rn 'waves\|Waves\|WAVES' src/` — fix all except wire-format constants

### Phase 2 — Bulletproof

1. Replace Jest with Vitest (`vitest.config.ts`, update test imports)
2. Enable `strict: true` in `tsconfig.json`, fix all type errors
3. Add Biome (`biome.json` extending root), remove ESLint/Prettier configs
4. Add Lefthook (`lefthook.yml`) for commit-time enforcement
5. Run `biome check --write .` — auto-fix formatting and lint issues
6. Run `tsc --noEmit` — fix all type errors
7. Run `vitest run --coverage` — verify thresholds met

### Phase 3 — Modernize

1. Replace tsup/tsc/webpack/rollup with tsdown (`tsdown.config.ts`)
2. Configure ESM-only output (`"type": "module"` in package.json)
3. Set up `exports` field with proper `types` + `import` conditions
4. Add `publint`, `attw`, `size-limit` validation scripts
5. Enable `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`
6. Run `knip` — remove dead exports, unused deps, orphaned files
7. Add `verbatimModuleSyntax` where feasible

### Phase 4 — Audit

1. Run grep audit for dangerous patterns (`eval`, `Math.random`, `http://`, etc.)
3. Verify all tests run offline (no network calls)
4. Document any remaining deviations in this STATUS.md
5. Mark package as ✅ in per-package status table

**KNOWN-1: License is GPL-3.0 (upstream WhisperSystems — cannot be relicensed)**

**Risk:** LOW | Derived from WhisperSystems/curve25519-java (GPL-3.0). Cannot relicense without the original author granting a separate license; GPL-3.0 propagates to all derivative works. All consumers must be aware they are linking a GPL-3.0 library. No violation in current deployment — DCC node links under the same GPL-3.0 terms as the upstream Waves node. **Resolution path:** If non-copyleft license required, write a fully independent Curve25519 implementation or use Bouncy Castle `X25519Agreement`.

**KNOWN-2: `NativeCurve25519Provider` uses JNA reflection — no compile-time type safety**

**Risk:** LOW | JNA's `Native.load()` uses reflection at runtime to match Java method signatures to native symbols. ABI mismatch surfaces as `UnsatisfiedLinkError` at runtime, not at compile time. Stable and matches the upstream approach. **Resolution path:** Future native security hardening sprint — migrate to explicit JNI with C glue, or replace with pure-Java Bouncy Castle `X25519Agreement`.

**KNOWN-3: VRF implementation uses a non-standard Unique Signature scheme (not RFC 9381)**

**Risk:** LOW | `calculateVrfSignature` / `verifyVrfSignature` implement the Waves/DCC-specific VRF construction. Predates and is not interoperable with RFC 9381 (ECVRF). The scheme is cryptographically secure under standard Curve25519 assumptions but not portable to standard ECVRF implementations. Changing it would be a hard fork. **Resolution path:** If RFC 9381 interoperability is ever required, introduce as a NEW VRF method alongside the existing one.
